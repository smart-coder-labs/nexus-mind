# ADR-002: Gestor de Base de Datos para el Core de Memoria

> **Estado**: Aceptado (con corrección)
> **Fecha**: Mayo 2026 (v2 — corregido: memoria compartida)
> **Contexto**: Decisión del motor de base de datos para el sistema de memoria persistente de NexusMind
> **Decisión**: SQLite (free tier, <30 users) → Postgres (enterprise tier, >30 users)
> **Nota**: v1 de este ADR asumía sharding por proyecto. **Corregido**: la memoria es compartida por toda la organización en un solo pool. El aislamiento es lógico (ABAC), no físico (archivos separados).
> **Consecuencias**: Ver sección 7

---

## 1. Contexto

NexusMind necesita un motor de base de datos para su core de memoria que cumpla:

| # | Requisito | Crítico |
|---|-----------|---------|
| R1 | **Zero-dependency embedido** — single binary, sin servidor externo | P0 |
| R2 | **FTS5 (Full-Text Search)** — búsqueda textual rápida en memoria | P0 |
| R3 | **Embeddings / vector search** — búsqueda semántica híbrida | P0 |
| R4 | **Transaccional ACID** — cada save es consistente | P0 |
| R5 | **Concurrencia multi-usuario** — >100 conexiones simultáneas | P0 |
| R6 | **Aislamiento multi-organización** — la memoria se filtra por políticas de acceso, no por archivos separados | P0 |
| R7 | **Redacción al vuelo** — filtrar datos sensibles en queries | P0 |
| R8 | **Merkle audit trail** — log inmutable verificable | P0 |
| R9 | **Replicación cloud opcional** — sync con servidor central | P1 |
| R10 | **On-premise ARM** — Raspberry Pi, servidores ARM64 | P1 |
| R11 | **Exportabilidad** — sin vendor lock-in de base de datos | P1 |

Este ADR evalúa 6 gestores de base de datos contra estos requisitos.

---

## 2. Gestores Evaluados

### 2.1 SQLite (incluyendo extensions: FTS5, sqlite-vec)

| Aspecto | Detalle |
|---------|---------|
| **Tipo** | Embedida, serverless, zero-config |
| **Licencia** | Dominio público |
| **Lenguaje** | C (bindings en Rust: `rusqlite`, `libsql`) |
| **Storage** | Single file `.db` por instancia (o `:memory:`) |
| **Concurrencia** | WAL mode: multiple readers, single writer |
| **FTS** | FTS5 nativo (tokenizadores customizables) |
| **Vectores** | sqlite-vec (extension community, ~70% del espacio vectorial completo) |
| **Transacciones** | ACID, serializable isolation |
| **Tamaño binario** | ~600KB (bundled con Rust) |

**Ventajas**:

- **Zero-dependency**: El binario de NexusMind no necesita Postgres, MySQL ni nada corriendo. `rusqlite` embebe SQLite directamente. El usuario hace `cargo install nexusmind` y ya.
- **FTS5 nativo**: No hay que instalar nada extra. FTS5 viene incluido en SQLite desde 2016. Tokenización custom para español, inglés, código fuente.
- **sqlite-vec**: Extensión vectorial para embeddings. Índice IVF-PQ con búsqueda coseno. Suficiente para miles de vectores sin servidor externo.
- **WAL mode**: Permite lecturas concurrentes mientras se escribe. Para equipos de 5-20 developers es más que suficiente.
- **On-prem ARM**: SQLite funciona en cualquier arquitectura. Raspberry Pi, servidores ARM64, lo que sea.
- **Backup trivial**: Copiar el `.db` file. `rsync`, `scp`, `git-lfs`. No hay que hacer `pg_dump`.
- **Merkle audit trail**: Se puede implementar directamente sobre SQLite con filas inmutables y hashes encadenados.

**Debilidades**:

| Debilidad | Impacto | Mitigación |
|-----------|---------|------------|
| **Single writer** | Solo una escritura simultánea. Múltiples escritores compiten por el lock. | WAL mode reduce contención. Para <50 developers, imperceptible. Para >50, sharding por proyecto (cada proyecto su propio `.db`). |
| **No clustering** | No hay replicación nativa. Cada instancia tiene su archivo. | Replicación vía sync engine (git o cloud). Proyecto diseñado para eso. |
| **Límite de tamaño** | ~140TB teórico, ~50TB práctico. | No es problema real. El tamaño típico de memoria de un proyecto son megas, no teras. |
| **Sin control de acceso** | No hay users/roles nativos. Cualquiera con acceso al archivo lee todo. | NexusMind implementa auth/ABAC **encima** de SQLite. El archivo nunca se expone directamente. |
| **FTS5 sin stemming multilingüe** | El tokenizador simple no hace stemming (raíces de palabras). | Tokenizador custom en Rust para español/inglés/código. `rusqlite` permite registrar tokenizadores. |
| **sqlite-vec limitado** | No es pgvector (Postgres). El índice IVF-PQ tiene ~85% de recall en datasets grandes. | Para el caso de uso (miles de entradas, no millones), es suficiente. Si se necesita más, ONNX + búsqueda en memoria con `candle`. |

**Benchmarking mental**:

```
Operación                | SQLite (WAL) | Notas
------------------------|-------------|-------------------------------------------
mem_save (insert)       | ~150μs      | Single row, synchronous
mem_search FTS5 (10k)   | ~2ms        | Full-text, 10k documentos
mem_search semantic     | ~20ms       | sqlite-vec, 10k embeddings dim 384
mem_get (by id)         | ~30μs       | Primary key lookup
mem_context (last 20)   | ~100μs      | Ordenado por timestamp, 20 rows
batch insert (100)      | ~2ms        | Transacción única
Concurrencia (100 rdrs) | ~500μs      | WAL mode, lectores sin bloqueo
```

### 2.2 LibSQL (Turso)

| Aspecto | Detalle |
|---------|---------|
| **Tipo** | Fork de SQLite con replicación + embedido |
| **Licencia** | Apache 2.0 |
| **Rust binding** | `libsql` crate (oficial) |
| **Concurrencia** | WAL mode + replicas de lectura vía HTTP |
| **FTS** | FTS5 (hereda de SQLite) |
| **Vectores** | sqlite-vec (hereda) |
| **Transacciones** | ACID, con replicación síncrona opcional |

**Ventajas sobre SQLite vanilla**:

- **Replicación nativa**: LibSQL permite replicación embedded → servidor vía HTTP. Ideal para el modelo local-first de NexusMind.
- **Embedded server**: Puedes correr `sqld` como servidor para acceso remoto sin perder la compatibilidad con SQLite.
- **Misma API que SQLite**: El binding `libsql` para Rust es compatible con `rusqlite`. Migración trivial.
- **Concurrencia vía HTTP**: Si el embedded writer es cuello de botella, puedes desplegar `sqld` y conectar desde múltiples procesos.

**Debilidades**:

| Debilidad | Impacto |
|-----------|---------|
| **Madurez menor** | LibSQL tiene ~3 años. SQLite tiene 25+. Menos probado en producción. |
| **Ecosistema más pequeño** | Menos extensions, menos documentación. |
| **Capa de replicación añade complejidad** | Si falla la red entre embedded y server, hay conflictos de merge. |
| **Fork que se aleja de upstream** | LibSQL ha hecho cambios que rompen compatibilidad con SQLite vanilla en algunos bordes. |

### 2.3 DuckDB

| Aspecto | Detalle |
|---------|---------|
| **Tipo** | Embedida, orientada a columnas, OLAP |
| **Licencia** | MIT |
| **Rust binding** | `duckdb` crate |
| **Concurrencia** | Single-process, no diseñado para multi-writer |
| **FTS** | No nativo (extension community, básica) |
| **Vectores** | No nativo |

**Ventajas**:

- **Analítico**: Queries agregadas en memoria son extremadamente rápidas. Ideal para dashboards y reporting.
- **Columnar**: Si almacenas metadatos estructurados (tags, tipos, timestamps), DuckDB comprime y escanea más rápido que SQLite.
- **Embedido**: También zero-dependency, single binary.

**Debilidades para NexusMind**:

| Debilidad | Impacto |
|-----------|---------|
| **Sin FTS5 nativo** | Tendrías que implementar búsqueda textual aparte (Tantivy). Dos engines de búsqueda. |
| **Sin concurrencia multi-writer** | Un solo proceso. No escala para equipos. |
| **Orientado a OLAP, no OLTP** | DuckDB optimiza para lecturas analíticas, no para writes transaccionales rápidos. Cada `mem_save` sería más lento que en SQLite. |
| **Caso de uso incorrecto** | DuckDB es para data lakes y analytics, no para un store transaccional de memoria. |

**Veredicto**: Inadecuado como base de datos primaria. Podría usarse como **capa analítica** separada (reporting, dashboards), pero no como store de memoria transaccional.

### 2.4 PostgreSQL

| Aspecto | Detalle |
|---------|---------|
| **Tipo** | Servidor cliente-servidor |
| **Licencia** | PostgreSQL License |
| **Rust binding** | `sqlx`, `diesel`, `tokio-postgres` |
| **Concurrencia** | Multi-writer nativo, MVCC, escalado horizontal |
| **FTS** | `tsvector`/`tsquery` (poderoso, con stemming y diccionarios) |
| **Vectores** | `pgvector` (extension madura, HNSW, IVFFlat) |
| **Transacciones** | ACID, serializable, repeatable read, read committed |

**Ventajas**:

- **Concurrencia real**: Multi-writer con MVCC. Cientos de conexiones escribiendo simultáneamente sin lock contention.
- **pgvector**: El estándar de facto para búsqueda vectorial. Índice HNSW para búsqueda aproximada de alta precisión.
- **FTS maduro**: `tsvector` con stemming, diccionarios, ranking. Mejor que FTS5 de SQLite.
- **Roles y permisos nativos**: Row-Level Security, schemas, usuarios. Parte de la base de datos, no capa externa.
- **Replicación nativa**: Streaming replication, logical replication. Built-in.
- **Madurez**: 30+ años, el motor de base de datos más probado del mundo opensource.

**Debilidades para NexusMind**:

| Debilidad | Impacto | Mitigación |
|-----------|---------|------------|
| **No es embedido** | Postgres requiere un servidor instalado. Viola R1 (zero-dependency). | Usar Postgres solo en cloud mode. El embedded mode sigue siendo SQLite. |
| **Overhead operacional** | El usuario tiene que instalar/configurar/mantener Postgres. | En on-prem enterprise, ya tienen Postgres. Para dev individual, SQLite es suficiente. |
| **Binario grande** | ~50MB vs ~600KB de SQLite. Para single binary, no es viable. | El single binary siempre es SQLite. Postgres es opcional para cloud/enterprise. |
| **Backup complejo** | `pg_dump`, WAL archiving. No es tan simple como copiar un archivo. | Manageable en enterprise. Para dev, SQLite. |
| **Overkill para single-user** | Para un developer individual, tener que instalar Postgres es inaceptable. | SQLite es el default. Postgres es upgrade enterprise. |

**Veredicto**: Excelente para el **modo cloud/enterprise** de NexusMind, pero **inadecuado como default** por la violación de R1. La arquitectura correcta es **SQLite local-first con sync opcional a Postgres**.

### 2.5 RocksDB

| Aspecto | Detalle |
|---------|---------|
| **Tipo** | Embedida, LSM-tree, key-value |
| **Licencia** | Apache 2.0 (GPL incompatibilidad con binding C++) |
| **Rust binding** | `rocksdb` crate (bindings a C++ library) |
| **FTS** | No nativo |
| **Vectores** | No nativo |
| **Transacciones** | Optimistic transactions, no ACID completo |

**Ventajas**:

- **Write throughput**: LSM-tree optimizado para writes secuenciales. Mucho más rápido que SQLite en writes intensivos.
- **Embedido**: Zero-dependency, single binary.
- **Compresión**: Bloques comprimidos por defecto (Snappy, ZSTD). Menos espacio en disco.

**Debilidades**:

| Debilidad | Impacto |
|-----------|---------|
| **No es relacional** | No hay SQL, no hay joins, no hay queries complejas. Tendrías que implementar tu capa de queries sobre key-value. |
| **Sin FTS** | No hay búsqueda textual. Tendrías que indexar en Tantivy aparte. |
| **Sin transacciones ACID** | RocksDB tiene optimistic transactions, pero no el mismo nivel de aislamiento que SQLite. Para audit trail, es crítico. |
| **Read amplification** | Las lecturas en LSM-tree son más lentas que en B-tree (SQLite). Para `mem_search`, SQLite gana. |
| **Rust bindings problemáticos** | `rocksdb` crate enlaza con librería C++ en tiempo de compilación. Compilación cruzada a ARM es problemática. |
| **Debuggabilidad** | No puedes abrir un archivo .db de RocksDB con una herramienta estándar. SQLite puedes abrirlo con cualquier cliente SQL. |
| **GPL incompatibilidad** | RocksDB es GPL, el binding `rocksdb` tiene licencia Apache 2.0 pero la librería subyacente no. Riesgo legal. |

**Veredicto**: Inadecuado. Es un motor KV, no un motor relacional con FTS. Usar RocksDB para un sistema de memoria con búsqueda semántica y relacional es forzar el tool incorrecto.

### 2.6 FoundationDB

| Aspecto | Detalle |
|---------|---------|
| **Tipo** | Distribuido, key-value, ACID |
| **Licencia** | Apache 2.0 |
| **Rust binding** | `foundationdb` crate |
| **FTS** | No nativo (hay capas sobre FDB) |
| **Vectores** | No nativo |
| **Transacciones** | ACID, serializable, multi-key |

**Ventajas**:

- **Distribuido nativo**: Escala horizontalmente. Múltiples máquinas, un solo cluster.
- **ACID en distributed**: Transacciones multi-key con Serializable isolation, incluso en cluster. Casi único en el mercado.
- **Determinista**: FoundationDB garantiza que una transacción correcta en test lo será en producción. No hay race conditions.
- **Performance**: 1M+ transacciones/segundo en cluster.

**Debilidades**:

| Debilidad | Impacto |
|-----------|---------|
| **No es embedido** | FoundationDB es un cluster, no un single binary. Viola R1 completamente. |
| **Operacional complejo** | FDB requiere un cluster de mínimo 3 máquinas. Overkill total para un core de memoria. |
| **No relacional** | Es KV. No hay SQL, FTS, ni vectores. Tendrías que construir todo desde cero. |
| **Ecosistema pequeño** | Pocos bindings, poca comunidad, documentación técnica densa. |
| **Latencia de red** | Cada transacción requiere al menos un RTT al cluster. Para operaciones locales, es más lento que SQLite. |

**Veredicto**: El motor correcto para una base de datos global distribuida (Apple lo usa para iCloud), pero **totalmente inadecuado** para el core de memoria local-first de NexusMind.

### 3.3 Árbol de Decisión (revisado con memoria compartida)

```
¿Cuántos usuarios escriben al pool compartido de memoria?
  │
  ├─ <30 usuarios → SQLite (rusqlite + WAL + FTS5 + sqlite-vec)
  │                  ← **Caso default** (free tier)
  │                  Backup: nexusmind export → archivo
  │
  ├─ 30-50 usuarios → SQLite + WAL mode + batch writes
  │                    ← **Monitorear**: si contención >5ms, migrar
  │                    Sync a Postgres recomendado como respaldo
  │
  ├─ 50-100 usuarios → Postgres (sqlx + pgvector + RLS)
  │                     ← **Enterprise tier**
  │                     SQLite local para dev individual
  │                     Postgres central para memoria compartida
  │
  └─ 100+ usuarios → Postgres + connection pooling (PgBouncer)
                      ← **Enterprise tier**
                      Sharding por organización si multi-tenant
```

**Nota importante**: La decisión no depende del tamaño de la empresa, sino de
**cuántas escrituras concurrentes** recibe el pool de memoria compartida.
Un equipo de 5 developers con agentes autónomos escribiendo 100 memorias/minuto
puede saturar SQLite más rápido que 50 developers que escriben 5/día.

## 4. Análisis Profundo de SQLite

### 4.1 ¿Por qué SQLite gana para el caso default?

1. **Es el motor que Engram ya usa** — y funciona bien para memoria de proyectos.
2. **FTS5 es nativo** — la extensión de búsqueda textual viene incluida. No hay que instalar nada.
3. **Zero operaciones** — el usuario no configura nada. `nexusmind serve` y ya está.
4. **Backup trivial** — el archivo `.db` es transportable. Ideal para el modelo local-first.
5. **On-prem viable** — Raspberry Pi, VPS de 512MB, servidor ARM64. Todo funciona.
6. **sqlite-vec** — cubre el caso de búsqueda semántica para miles de embeddings sin servidor externo.
7. **25 años de madurez** — el software más probado del planeta. Más de 1 trillón de bases de datos SQLite en existencia.

### 4.2 CORRECCIÓN CRÍTICA: La memoria es compartida para TODA la organización

El análisis original de este ADR asumía que la memoria se podía particionar por proyecto en archivos `.db` separados, y que el sharding resolvía la contención de escritura.

**Eso es incorrecto para NexusMind.**

La memoria de NexusMind es **un pool único compartido por toda la organización**. Todos los usuarios leen y escriben en el mismo espacio de memoria. El aislamiento no se logra separando archivos, sino mediante **políticas ABAC y etiquetas de sensibilidad** que filtran qué puede ver cada quién — pero los datos coexisten en el mismo store.

Esto tiene implicaciones profundas:

1. **No hay sharding por proyecto que mitigue el single writer** — todos los writes van al mismo archivo `.db`.
2. **La concurrencia de escritura es el problema central**, no un edge case.
3. **Una organización de 100 developers** escribiendo memorias simultáneamente satura el single writer de SQLite.
4. **El aislamiento de memoria es lógico, no físico** — todo está en la misma tabla, filtrado por políticas.
5. **El archivo `.db` contiene TODOS los datos de la organización** — si alguien accede al archivo directamente, tiene todo. La seguridad del archivo es crítica.

### 4.3 Re-evaluación de SQLite con memoria compartida

**SQLite sigue siendo viable para equipos pequeños-medianos** (<30 developers, <100 writes/hora). Con WAL mode, las lecturas no se bloquean. La escritura serializada ~150μs por save significa que incluso con 10 writes simultáneos, la cola se vacía en ~1.5ms. Imperceptible para humanos.

**Pero para organizaciones grandes** (>50 developers) o con alta frecuencia de writes, el single writer de SQLite es un problema real.

Además, el **almacenamiento de embeddings** escala mal en SQLite compartido: si 50 developers guardan memorias con vectores de 384 dimensiones, el archivo `.db` crece rápido y las búsquedas vectoriales compiten con los writes.

**Nuevo veredicto para SQLite con memoria compartida:**

| Tamaño de organización | ¿SQLite funciona? | Alternativa recomendada |
|----------------------|-------------------|------------------------|
| <10 developers | ✅ Sí, perfecto | SQLite |
| 10-30 developers | ✅ Sí, con WAL mode | SQLite + WAL |
| 30-50 developers | ⚠️ Posible, monitorear | SQLite + WAL, preparar migración |
| 50-100 developers | ❌ Single writer cuello de botella | LibSQL o Postgres |
| 100+ developers | ❌ No escala | Postgres con connection pooling |

### 4.4 Estrategia Recomendada con Memoria Compartida

**Arquitectura escalonada (tiered):**

```
┌──────────────────────────────────────────────┐
│          NexusMind Core (Rust)                │
│                                                │
│  ┌──────────────────────────────────────┐     │
│  │   Store Abstraction Trait            │     │
│  │   (misma API para todos los backends)│     │
│  └──────────┬───────────────────────────┘     │
│             │                                  │
│  ┌──────────┴──────────┐  ┌───────────────┐   │
│  │ SQLiteBackend       │  │ PostgresBackend│   │
│  │ (free tier)         │  │ (paid tier)   │   │
│  │ - Hasta ~30 users   │  │ - Escalable   │   │
│  │ - Single file .db   │  │ - pgvector    │   │
│  │ - Sin servidor      │  │ - RLS nativo  │   │
│  └─────────────────────┘  └───────────────┘   │
│                                                │
│  ┌──────────────────────────────────────┐     │
│  │   Sync Engine (SQLite → Postgres)    │     │
│  │   - Local-first: escribe en SQLite   │     │
│  │   - Replica async a Postgres         │     │
│  │   - Postgres es el source of truth   │     │
│  │     para queries compartidas         │     │
│  └──────────────────────────────────────┘     │
└──────────────────────────────────────────────┘
```

**Flujo para organizaciones con SQLite local + Postgres cloud:**

```
1. Cada developer escribe a su SQLite local (rápido, sin latencia de red)
2. Sync engine replica a Postgres cloud (async, batch cada 30s)
3. Lecturas de memoria compartida se hacen contra Postgres
4. Postgres maneja la concurrencia real con MVCC
5. Row-Level Security en Postgres filtra por rol/usuario directamente en la query
6. pgvector maneja búsqueda semántica a escala
```

**Para free tier / equipos pequeños:**

```
1. Todos escriben al mismo SQLite compartido (WAL mode)
2. El Auth Gateway filtra qué puede leer cada quién antes de llegar a SQLite
3. Las queries de búsqueda incluyen el user_id y los filtros de sensibilidad
4. sqlite-vec para búsqueda vectorial básica
5. Sync engine replica a un Postgres central (backup + futuro upgrade)
```

### 4.5 Resumen: SQLite con memoria compartida

SQLite **sí es viable** para el caso default (equipos <30 personas). Pero la razón por la que funciona no es el sharding, sino:

1. **WAL mode**: las lecturas no se bloquean durante escrituras. 100 queries de lectura corren en paralelo.
2. **Latencia de escritura baja**: ~150μs. Incluso con 10 writers simultáneos, la cola se vacía en <2ms.
3. **Caching en Rust**: el policy engine y el cache de embeddings reducen la carga en SQLite.
4. **Batch writes**: las escrituras se pueden agrupar en transacciones para reducir lock contention.

**Para equipos >30 personas, la respuesta es Postgres con pgvector**, no SQLite. Y el diseño del Store Abstraction Trait lo permite sin cambiar la aplicación.

### 4.6 Estrategia de Embeddings en SQLite (para memoria compartida)

```
Embedding model: all-MiniLM-L6-v2 (384 dims, ONNX)
Vector store: sqlite-vec con índice IVF-PQ
Búsqueda híbrida: FTS5 score + cosine similarity, weighted

Pesos por defecto:
  FTS5 weight: 0.6
  Semantic weight: 0.4
```

### 4.4 Benchmark Proyectado (memoria compartida)

Escenario: Organización con 15 developers, 6 meses de uso, ~5000 entradas en el pool compartido.

| Operación | SQLite (WAL) | Postgres (local) | Notas |
|-----------|--------------|------------------|-------|
| mem_save (with FTS5 index) | ~200μs | ~500μs | SQLite más rápido en single-writer |
| mem_search "auth middleware" | ~3ms | ~1.5ms | Postgres tsvector más optimizado |
| mem_search hybrid (FTS + vec) | ~25ms | ~18ms | pgvector HNSW > sqlite-vec IVF |
| mem_context (last 20) | ~100μs | ~200μs | Con cache, ambos rápidos |
| Policy eval (ABAC, 5 rules) | ~10μs | ~10μs | En Rust, no en DB |
| Audit log insert | ~50μs | ~150μs | Append-only, ambos rápidos |
| **10 writes simultáneos** | **~2ms (serial)** | **~500μs (paralelo)** | **Aquí Postgres gana** |
| **50 writes simultáneos** | **~10ms (cola)** | **~500μs (paralelo)** | **SQLite sufre contención** |
| **100 queries lectura + 10 writes** | **~3ms (WAL)** | **~500μs (MVCC)** | **WAL ayuda pero no iguala** |

**Conclusión**: Para <30 usuarios, SQLite es suficiente. Para >30, el single writer se nota. Para >50, Postgres es necesario.

---

## 5. Análisis por Caso de Uso

### 5.1 Concurrencia masiva (>100 writers) → Postgres

SQLite no escala para >50 writers concurrentes en el mismo proyecto. Postgres con MVCC y Row-Level Security es la opción correcta. Pero es un caso extremo para NexusMind; la mayoría de proyectos tienen 2-20 developers.

### 5.2 Analytics y reporting → DuckDB

Si se necesitara hacer queries analíticas pesadas sobre la memoria histórica (ej: "¿cuántos bugs se resolvieron por developer este mes?"), DuckDB como capa separada tendría sentido. Pero el store primario sigue siendo SQLite.

### 5.3 Distribuido global → FoundationDB

Para memoria compartida entre oficinas en múltiples continentes con consistencia fuerte, FoundationDB. Pero NexusMind es local-first con sync opcional.

### 5.4 Replicación fácil → LibSQL (Turso)

Si el modelo requiriera replicación automática sin configuración, LibSQL ganaría. Pero añade complejidad de red y conflictos de merge que no se justifican para el caso default.

## 6. Decisión y Arquitectura Propuesta

### 6.1 Decisión

**SQLite** (vía `rusqlite` con FTS5 + sqlite-vec) como motor de base de datos **default** para el core de memoria de NexusMind, con **migración opcional a Postgres** en modo cloud/enterprise.

pub trait MemoryStore: Send + Sync {
    async fn save(&self, memory: NewMemory) -> Result<MemoryId>;
    async fn search_fts(&self, query: &str, project: &ProjectId) -> Result<Vec<Memory>>;
    async fn search_hybrid(&self, query: &str, embedding: &[f32],
                           project: &ProjectId) -> Result<Vec<Memory>>;

    async fn delete(&self, id: MemoryId) -> Result<()>;
    async fn context(&self, project: &ProjectId, limit: u32) -> Result<Vec<Memory>>;
    async fn timeline(&self, id: MemoryId, window: u32) -> Result<Vec<Memory>>;
}

// SQLite implementation
pub struct SQLiteMemoryStore {
    conn: Connection,
    fts: FtsIndex,
    vec: VecIndex,
}

// Postgres implementation (cloud/enterprise)
pub struct PostgresMemoryStore {
    pool: PgPool,
}

// Factory
pub fn create_store(config: &StoreConfig) -> Box<dyn MemoryStore> {
    match config.engine {
        StoreEngine::SQLite => Box::new(SQLiteMemoryStore::open(&config.path)),

### 6.4 Estrategia de Migración entre Engines

1. **Default**: SQLite local. Cada proyecto su propio `.db`.
2. **Upgrade a Postgres**: `nexusmind migrate --to postgres://...` — sync engine copia los datos. Sin downtime, SQLite sigue siendo readable.
3. **Modo híbrido**: El store escribe en SQLite local y replica a Postgres async. Backup central sin perder rendimiento local.
4. **Rollback**: `nexusmind migrate --to sqlite://...` — descarga de Postgres a SQLite. Zero lock-in.

### 6.5 Schema SQLite (diseñado para memoria compartida)

El schema refleja que TODA la memoria de la organización vive en las mismas tablas.
El aislamiento se logra mediante filtros ABAC en tiempo de query, no separando archivos.

```sql
-- Organizaciones (cada organización tiene su propia base de datos)
CREATE TABLE organizations (
  id TEXT PRIMARY KEY,               -- UUID
  name TEXT NOT NULL,
  slug TEXT NOT NULL UNIQUE,
  created_at TEXT NOT NULL DEFAULT (datetime('now'))
);

-- Proyectos dentro de la organización (agrupación lógica, no física)
CREATE TABLE projects (
  id TEXT PRIMARY KEY,               -- UUID
  org_id TEXT NOT NULL REFERENCES organizations(id),
  name TEXT NOT NULL,
  description TEXT,
  sensitivity_default TEXT NOT NULL DEFAULT 'internal',
  created_at TEXT NOT NULL DEFAULT (datetime('now'))
);

-- Tabla principal de memoria (COMPARTIDA para toda la organización)
CREATE TABLE memories (
  id TEXT PRIMARY KEY,              -- UUID v7 (chronológico)
  org_id TEXT NOT NULL REFERENCES organizations(id),
  project_id TEXT,                  -- Proyecto al que pertenece (nullable, opcional)
  title TEXT NOT NULL,
  memory_type TEXT NOT NULL,        -- 'bugfix', 'architecture', 'decision', etc.
  content TEXT NOT NULL,
  sensitivity TEXT NOT NULL DEFAULT 'internal', -- public, internal, sensitive, critical, audit_only
  tags TEXT,                        -- JSON array para filtrado
  tool_id TEXT,                     -- 'cursor', 'claude-code', etc.
  user_id TEXT,                     -- Quién creó la memoria
  user_role_at_write TEXT,          -- Rol del usuario al momento de escribir (para auditoría retrospectiva)
  topic_key TEXT,                   -- Para upserts
  revision_count INT NOT NULL DEFAULT 1,
  duplicate_count INT NOT NULL DEFAULT 0,
  prompt_context TEXT,              -- Prompt snapshot del agente
  embedding BLOB,                   -- Vector f32 serializado (384 dims) para búsqueda semántica
  created_at TEXT NOT NULL DEFAULT (datetime('now')),
  updated_at TEXT NOT NULL DEFAULT (datetime('now')),
  deleted_at TEXT,                  -- Soft delete
  
  FOREIGN KEY (org_id) REFERENCES organizations(id)
);

-- Índice crítico para queries filtradas por organización
CREATE INDEX idx_memories_org ON memories(org_id);
CREATE INDEX idx_memories_org_sensitivity ON memories(org_id, sensitivity);
CREATE INDEX idx_memories_org_user ON memories(org_id, user_id);
CREATE INDEX idx_memories_org_tool ON memories(org_id, tool_id);
CREATE INDEX idx_memories_org_type ON memories(org_id, memory_type);
CREATE INDEX idx_memories_org_topic ON memories(org_id, topic_key);

-- FTS5 virtual table (sobre TODA la memoria de la organización)
CREATE VIRTUAL TABLE memories_fts USING fts5(
  title, content, tags,
  content=memories,
  content_rowid=rowid,
  tokenize='unicode61 remove_diacritics 2',
  prefix='2 3 4'                   -- Búsqueda por prefijo para autocomplete
);

-- Triggers para mantener FTS5 sincronizado
CREATE TRIGGER memories_ai AFTER INSERT ON memories BEGIN
  INSERT INTO memories_fts(rowid, title, content, tags)
  VALUES (new.rowid, new.title, new.content, new.tags);
END;

CREATE TRIGGER memories_ad AFTER DELETE ON memories BEGIN
  INSERT INTO memories_fts(memories_fts, rowid, title, content, tags)
  VALUES ('delete', old.rowid, old.title, old.content, old.tags);
END;

CREATE TRIGGER memories_au AFTER UPDATE ON memories BEGIN
  INSERT INTO memories_fts(memories_fts, rowid, title, content, tags)
  VALUES ('delete', old.rowid, old.title, old.content, old.tags);
  INSERT INTO memories_fts(rowid, title, content, tags)
  VALUES (new.rowid, new.title, new.content, new.tags);
END;

-- Sessions (por usuario, dentro de la organización)
CREATE TABLE sessions (
  id TEXT PRIMARY KEY,
  org_id TEXT NOT NULL REFERENCES organizations(id),
  user_id TEXT NOT NULL,
  tool_id TEXT,
  started_at TEXT NOT NULL DEFAULT (datetime('now')),
  ended_at TEXT,
  summary TEXT,
  FOREIGN KEY (org_id) REFERENCES organizations(id)
);

-- Audit log (append-only, inmutable, compartido para toda la org)
CREATE TABLE audit_entries (
  id TEXT PRIMARY KEY,
  org_id TEXT NOT NULL REFERENCES organizations(id),
  prev_hash TEXT NOT NULL,          -- SHA256 del entry anterior (encadenamiento)
  merkle_root TEXT NOT NULL,        -- Raíz del árbol de Merkle (verificación por lote)
  timestamp TEXT NOT NULL DEFAULT (datetime('now')),
  action TEXT NOT NULL,             -- 'memory:read', 'memory:write', 'policy:evaluate', etc.
  user_id TEXT,
  tool_id TEXT,
  metadata TEXT,                    -- JSON con detalles de la acción
  signature TEXT,                   -- Ed25519 signature para verificación
  
  FOREIGN KEY (org_id) REFERENCES organizations(id)
);

CREATE INDEX idx_audit_org ON audit_entries(org_id);
CREATE INDEX idx_audit_org_time ON audit_entries(org_id, timestamp);
CREATE INDEX idx_audit_org_user ON audit_entries(org_id, user_id);
CREATE INDEX idx_audit_org_action ON audit_entries(org_id, action);

-- Políticas (globales por organización)
CREATE TABLE policies (
  id TEXT PRIMARY KEY,
  org_id TEXT NOT NULL REFERENCES organizations(id),
  name TEXT NOT NULL,
  yaml_definition TEXT NOT NULL,    -- Definición completa en YAML
  enabled BOOLEAN NOT NULL DEFAULT true,
  version INT NOT NULL DEFAULT 1,
  priority INT NOT NULL DEFAULT 100, -- Orden de evaluación (menor = primero)
  created_by TEXT,
  created_at TEXT NOT NULL DEFAULT (datetime('now')),
  updated_at TEXT NOT NULL DEFAULT (datetime('now')),
  
  FOREIGN KEY (org_id) REFERENCES organizations(id)
);

-- Roles (definidos por organización)
CREATE TABLE roles (
  id TEXT PRIMARY KEY,
  org_id TEXT NOT NULL REFERENCES organizations(id),
  name TEXT NOT NULL,
  display_name TEXT NOT NULL,
  description TEXT,
  extends TEXT,                     -- JSON array de role IDs que hereda
  yaml_definition TEXT NOT NULL,
  version INT NOT NULL DEFAULT 1,
  enabled BOOLEAN NOT NULL DEFAULT true,
  created_by TEXT,
  created_at TEXT NOT NULL DEFAULT (datetime('now')),
  updated_at TEXT NOT NULL DEFAULT (datetime('now')),
  
  FOREIGN KEY (org_id) REFERENCES organizations(id),
  UNIQUE(org_id, name)
);

-- Miembros de la organización con sus roles
CREATE TABLE org_members (
  user_id TEXT NOT NULL,
  org_id TEXT NOT NULL REFERENCES organizations(id),
  role_id TEXT NOT NULL REFERENCES roles(id),
  project_overrides TEXT,           -- JSON con permisos override por proyecto
  granted_by TEXT,
  granted_at TEXT NOT NULL DEFAULT (datetime('now')),
  
  PRIMARY KEY (user_id, org_id),
  FOREIGN KEY (org_id) REFERENCES organizations(id)
);
```

## 7. Consecuencias

### 7.1 Positivas

- **Simplicidad operacional**: Zero-dependency. El usuario instala un binario y funciona.
- **On-prem viable**: Cualquier hardware, cualquier arquitectura, incluyendo Raspberry Pi.
- **Backup trivial**: Copiar un archivo. Ideal para el modelo local-first.
- **Syncing manejable**: SQLite → git chunks replica el modelo de Engram. SQLite → Postgres es directo.
- **Zero lock-in**: El schema es SQL estándar. Migrar a Postgres, MySQL, DuckDB es posible sin cambiar la aplicación — solo el backend del trait.
- **Familiaridad**: SQLite es la base de datos más usada del mundo. Cualquier developer puede debuguear el archivo `.db`.

### 7.2 Negativas

- **Single writer**: Para >50 developers en un proyecto, necesitas migrar a Postgres.
- **Vector search limitado**: sqlite-vec no es pgvector. Para datasets grandes (>50k vectores), necesitas ONNX o Postgres.
- **Sin RLS nativo**: La seguridad es responsabilidad de la capa de aplicación.
- **Sin replicación nativa**: Hay que implementarla con el sync engine. No es automática.

### 7.3 Mitigaciones

| Riesgo | Mitigación |
|--------|------------|
| Contención de escritura en equipos grandes | Sharding por proyecto + WAL mode. Cada proyecto es un archivo independiente. |
| Límite de búsqueda vectorial | sqlite-vec para entry point. ONNX + Candle para escalar. pgvector en cloud. |
| Sin control de acceso nativo | Auth layer en Rust con Policy Engine. El archivo .db nunca se expone. |
| Sin replicación nativa | Sync engine con 3 modos: git chunks, libSQL HTTP, Postgres logical replication. |
| FTS5 sin stemming | Tokenizador custom en Rust registrado en rusqlite. |
