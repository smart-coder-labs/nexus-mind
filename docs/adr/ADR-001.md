# ADR-001: Lenguaje de Implementación del Core de Memoria

> **Estado**: Aceptado
> **Fecha**: Mayo 2026
> **Contexto**: Decisión de lenguaje para reescribir Engram como el core de memoria persistente de NexusMind
> **Decisión**: Rust
> **Consecuencias**: Ver sección 6

---

## 1. Contexto

NexusMind necesita un sistema de memoria persistente similar a [Engram](https://github.com/Gentleman-Programming/engram) pero adaptado a las necesidades enterprise: multi-usuario, multi-proyecto, con aislamiento de memoria, política de acceso granular, audit trail criptográfico y búsqueda semántica híbrida.

Engram está implementado en Go (~3,000 líneas de Go, SQLite + FTS5, MCP server, CLI, TUI). Es un proyecto excelente para el caso de uso individual, pero no cumple los requisitos de NexusMind sin cambios arquitectónicos profundos.

Este ADR documenta la decisión del lenguaje de implementación para el rewrite.

### 1.1 Requisitos del Core de Memoria de NexusMind

| # | Requisito | Crítico |
|---|-----------|---------|
| R1 | Persistencia SQLite + FTS5 | P0 |
| R2 | Búsqueda semántica híbrida (FTS5 + embeddings) | P0 |
| R3 | Concurrencia multi-usuario (>100 conexiones simultáneas) | P0 |
| R4 | Aislamiento de memoria por proyecto + sensibilidad | P0 |
| R5 | Redacción automática de datos en tiempo real | P0 |
| R6 | Audit trail inmutable con verificación criptográfica | P0 |
| R7 | Policy engine ABAC <50ms por evaluación | P0 |
| R8 | MCP server, HTTP API, CLI, TUI | P1 |
| R9 | Distribución single-binary cross-platform | P1 |
| R10 | Sync cloud opcional (BYO Postgres) | P1 |
| R11 | On-premise deploy en ARM (Raspberry Pi, etc.) | P2 |

### 1.2 Limitaciones de Engram (Go) para NexusMind

| Aspecto | Engram (Go) | Problema para NexusMind |
|---------|-------------|-------------------------|
| Concurrencia | Mutex global sobre SQLite | >100 conexiones compitiendo por un lock — cuello de botella |
| FTS5 puro | Solo búsqueda textual | Necesitamos hybrid search (FTS + embeddings) |
| Sin policy engine | No existe | Necesitamos RBAC/ABAC en <50ms |
| Audit simple | Append log básico | Necesitamos merkle audit trail |
| Sin aislamiento | Single-user | Necesitamos multi-tenant con isolation |
| GC pauses | GC del runtime | Latencia impredecible en evaluaciones de política |

## 2. Opciones Consideradas

### 2.1 Opción A: Go (fork de Engram)

Mantener Go, forkear Engram y añadir las capas de auth, policy, isolation.

**Ventajas**:
- Menor esfuerzo inicial (aprovechar ~80% de Engram)
- Ecosistema maduro de herramientas (Bubbletea, sqlite, Charming)
- Compilación rápida, despliegue simple
- Equipo más fácil de contratar

**Desventajas**:
- GC overhead en evaluaciones de política de alta frecuencia
- Concurrencia sobre SQLite limitada por diseño de Go (goroutines no resuelven lock contention)
- No hay FTS5 + embeddings nativo (necesita FFI o wrapper)
- Audit trail criptográfico requiere librerías C
- Sin borrow checker — bugs de memoria en módulo de auth = CVE potencial

### 2.2 Opción B: Rust

Reescribir desde cero en Rust con arquitectura modular (crates).

**Ventajas**:
- Performance determinista, sin GC
- SQLite concurrente real con `rusqlite` + WAL + `tokio`
- Ecosistema de búsqueda: `tantivy` para FTS + `candle`/`ort` para embeddings
- Audit trail criptográfico nativo (`ed25519-dalek`, `merkle`)
- Borrow checker elimina bugs de memoria en auth module
- `clap` + `ratatui` + `axum` stack completo
- Cross-compilation nativa con `cargo-zigbuild`
- Ideal para on-prem ARM (Raspberry Pi)

**Desventajas**:
- Mayor esfuerzo inicial de escritura
- Curva de aprendizaje más alta para el equipo
- Compilación más lenta
- Ecosistema TUI menos maduro que Bubbletea (Go)

### 2.3 Opción C: Zig

**Ventajas**: Performance y control total, sin runtime.
**Desventajas**: Ecosistema pequeño, falta de librerías maduras para SQLite/FTS/embeddings, equipo difícil de formar. Descartado.

### 2.4 Opción D: C++

**Ventajas**: Performance máxima, control total.
**Desventajas**: Seguridad de memoria manual, build system complejo, falta de librerías modernas para MCP/server, TUI. Descartado.

## 3. Decisión: Rust

Se elige **Rust** como lenguaje de implementación para el core de memoria de NexusMind.

### 3.1 Criterios de Decisión

| Criterio | Peso | Go | Rust | Notas |
|----------|------|----|------|-------|
| Concurrencia SQLite | 10 | 5 | 9 | Go lock contention escala mal |
| Búsqueda semántica | 10 | 5 | 9 | tantivy > FTS5 puro |
| Latencia policy engine | 9 | 6 | 10 | Sin GC = latencia determinista |
| Audit criptográfico | 8 | 5 | 9 | Ed25519/merkle nativo |
| Seguridad de memoria | 9 | 6 | 10 | Borrow checker previene CVE |
| Multi-plataforma | 7 | 9 | 9 | Ambos excelentes |
| Single binary | 7 | 10 | 9 | Go gana en simplicidad |
| TUI | 5 | 7 | 6 | Bubbletea > ratatui (hoy) |
| Contratación | 6 | 8 | 6 | Go más fácil de contratar |
| Velocidad de desarrollo | 6 | 8 | 5 | Go más rápido para prototipar |
| **Total ponderado** | | **67** | **82** | |

### 3.2 Stack Técnico Propuesto

| Capa | Tecnología | Justificación |
|------|-----------|---------------|
| Runtime | Tokio (async) | Async nativo, scheduler cooperativo |
| HTTP/API | Axum | Middleware typed, integración con tower |
| CLI | Clap + Cargo-dist | Estándar de la industria |
| TUI | Ratatui | Terminal UI cross-platform |
| MCP | custom (tokio + serde_json) | Protocolo simple, sin dependencia pesada |
| SQLite | Rusqlite + WAL mode | Bindings directos, sin CGO |
| FTS | Tantivy | Search engine real, no solo token match |
| Embeddings | Candle (ONNX) o Ort | Modelos locales, sin dependencia Python |
| Policy | Custom engine (Rego-like) | Evaluación <50μs por regla |
| Audit | Ed25519 + Merkle tree | Verificación criptográfica |
| Auth | OIDC + JWT (openidconnect crate) | SSO enterprise |
| Serialización | Serde + JSON/MessagePack | Flexible, zero-copy deserialization |

## 4. Estrategia de Migración

### Fase 1: Core (Semanas 1-4)
- `nexusmind-core`: tipos compartidos
- `nexusmind-store`: SQLite + FTS5 básico (equivalente funcional a Engram)
- `nexusmind-mcp`: tools `mem_save`, `mem_search`, `mem_context`
- `nexusmind-cli`: `engram setup`, `engram serve`, `engram mcp`

**Resultado**: Drop-in replacement de Engram para un solo usuario. Misma API MCP.

### Fase 2: Auth + Aislamiento (Semanas 5-8)
- `nexusmind-auth`: SSO, JWT, custom roles, RBAC/ABAC
- `nexusmind-store/isolation.rs`: Memory isolation por proyecto + sensibilidad
- `nexusmind-store/redact.rs`: Redacción automática

**Resultado**: Multi-usuario funcional con políticas.

### Fase 3: Audit + Búsqueda (Semanas 9-12)
- `nexusmind-audit`: Merkle audit trail
- `nexusmind-store/fts.rs` + `embeddings.rs` + `hybrid.rs`: Búsqueda semántica
- `nexusmind-server`: HTTP API completa

**Resultado**: Feature parity con AUTH_SPEC.md.

### Fase 4: Interfaz + Sync (Semanas 13-16)
- `nexusmind-tui`: Terminal UI
- `nexusmind-sync`: Git + cloud sync
- Plugin adapters (Claude Code, Cursor, etc.)

**Resultado**: MVP completo de NexusMind core.

## 6. Consecuencias

### 6.1 Positivas
- Performance determinista sin GC — ideal para policy engine <50ms
- Concurrencia real sobre SQLite con WAL mode + `rusqlite`
- Búsqueda semántica híbrida nativa con `tantivy` + ONNX
- Audit trail criptográfico verifiable
- Cross-compilation a ARM para on-prem sin esfuerzo extra
- Borrow checker = bugs de memoria cero en auth module
- `cargo-dist` = instaladores nativos (brew, .deb, .rpm, .msi)

### 6.2 Negativas
- Mayor tiempo de desarrollo inicial (~16 semanas vs ~8 en Go)
- Curva de aprendizaje: el equipo necesita dominar Rust
- Compilación lenta: ~2-3 minutos en CI
- Ecosistema TUI menos maduro que Bubbletea
- Contratación más difícil que Go para developers AI

### 6.3 Mitigaciones
- Fase 1 entrega Engram-compatible en 4 semanas (mínimo producto funcional)
- TUI se pospone a Fase 4 (hasta entonces, CLI + web dashboard)
- CI caching de dependencias (`cargo chef`, `sccache`)
- Documentación interna de Rust para onboarding
- Contribuir a `ratatui` para mejorar el ecosistema
